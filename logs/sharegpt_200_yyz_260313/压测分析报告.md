## 二、vLLM 引擎侧证据（`prefill.log` / `decode.log`）

我对目录下 **6 个 batch 的 prefill/decode 日志**按 vLLM Engine 指标行做了全量解析与统计（并已生成图表 Excel）：

- **汇总图表**：`log/sharegpt_200_yyz_260313/vllm_engine_metrics_sweep.xlsx`  
- **每个 batch 的明细图表**：`batch_xx/batch_xx_vllm_engine_metrics_sweep.xlsx`

下面给出“能直接解释现象”的关键统计（P95/Max 来自引擎日志的逐 10s 采样行，非 AISBench 统计口径）。\n
### 1) Prefill 侧出现明显排队（Waiting）拐点

**Prefill Waiting（P95 / Max）**：

- batch_30：P95=0，Max=1  
- batch_40：P95=0，Max=15  
- batch_50：P95=0，Max=11  
- batch_60：P95=21，Max=27  
- batch_70：P95=34，Max=41  
- batch_140：P95=109，Max=112  

这与 AISBench 的 **TTFT** 从 50→60 开始爆炸式恶化完全一致：\n
- 30/40：TTFT ~0.65s（几乎无排队）\n
- 50：TTFT ~0.93s（仍可控）\n
- 60/70/140：Waiting P95 快速升高 → TTFT/E2EL 大幅变差\n

### 2) Decode 侧基本“被喂饱”，瓶颈不在 TPOT

**Decode Running（P95）** 基本贴近并发（30/40/50/60/70），说明 Decode 端长期有活干；同时 **Decode Waiting P95=0~1**，并不明显排队。结合 AISBench 的 **TPOT ~125–133ms**相对稳定，可判断：\n
- **主要瓶颈在 Prefill（以及 Prefill→Decode 的链路/调度），而不是 Decode token 生成速度本身。**

### 3) KV cache 与 prefix 命中随并发变化（有“效率下降”的信号）

从引擎日志统计看：\n
- **Decode KV cache usage P95** 在 50+ 时接近饱和（约 95%～98%），说明 Decode 端 KV 压力较大但仍维持生成吞吐。 \n
- **Prefix cache hit（P95）**：在低并发（30/40/50）更高（prefill ~87%），到 60/70/140 明显下降（prefill P95 ~77% → 74% → 61%）。这通常会放大 Prefill 侧计算压力（同样输入更难复用前缀）。\n

> 这部分更适合结合 `vllm_engine_metrics_sweep.xlsx` 的时序曲线看“下降发生在压测的哪个阶段/是否与 Waiting 上升同步”。\n

## 三、整体结论（基于全部 batch + 引擎侧证据）

### 1) 并发-吞吐-延迟的“可用区间”

- **低延迟区（推荐做交互体验/稳定性评估）**：batch_30～40\n
  - TTFT ~0.65s，Prefill Waiting P95=0，Prefill 吞吐 3600–3800 tok/s\n
- **吞吐优先区（推荐做容量/峰值吞吐评估）**：batch_50\n
  - Req/s 达到本次最高（0.802），TTFT ~0.93s 仍可控，Prefill Waiting P95=0\n
- **过载区（不建议作为长期运行点）**：batch_60 及以上\n
  - Prefill Waiting P95 迅速抬升（21→34→109）\n
  - TTFT/E2EL 急剧恶化（7s→15s→74s；E2EL 71s→78s→138s）\n
  - Prefill Token Throughput 断崖式下跌（324→155→33）\n

### 2) 关键瓶颈定位

**瓶颈 = Prefill 侧排队/处理能力不足（或其调度导致有效处理能力下降）**。证据链：\n
- AISBench：TTFT 从 50→60 开始飙升，E2EL 随并发增加明显变差\n
- 引擎日志：Prefill Waiting P95 从 0 变为 21/34/109；Decode 侧 Waiting 依旧很低、TPOT 稳定\n

## 四、异常与数据质量（只保留会影响结论/可行动项）

### 1) Failed Requests（各 batch 都有少量）

`aisbench.log` 显示每组有 35–82 个失败请求。结合 `decode.log`，主要是**个别多轮样本上下文过长**，导致固定 `max_tokens=512` 时出现 “输入 + 输出预算 > 8192” 的请求被服务端拒绝。\n
**建议**（影响失败率，也影响可比性）：\n
- 客户端/数据侧做 **动态 max_tokens**：`max_tokens = min(512, 8192 - input_tokens - safety_margin)`\n
- 或对超长轮次做截断/跳过，确保不同并发下“有效请求集合”一致\n

> 我没有在报告里展开栈追踪和工具自身 WARNING（它们不影响性能结论）。\n

## 五、可优化点（按优先级）

### 1) 先把“有效请求”对齐（必做）

- 解决超长上下文导致的失败请求（动态 max_tokens / 截断策略）\n
- 重新跑 30/40/50（建议至少各 1 次），保证不同并发的可比性\n

### 2) 针对 Prefill 过载的优化方向（核心）

- **并发控制/限流**：将长期运行点放在 **40–50**，避免进入 60+ 过载区\n
- **提升 Prefill 有效处理能力**（按你们当前可改动项选择）：\n
  - 尝试增大 `max_num_batched_tokens`（例如 256→512）观察 Prefill Waiting 与 TTFT 是否改善\n
  - 若资源允许，考虑给 Prefill 更多算力（卡数/实例）或拆分流量（多 Prefill 实例）\n
  - 结合 `vllm_engine_metrics_sweep.xlsx` 观察 prefix 命中下降是否与 Waiting 上升同步：若同步，优先排查“前缀复用策略/数据组织/会话切分”\n

### 3) 报表与监控（已就绪）

- 已生成 `vllm_engine_metrics_sweep.xlsx`：建议作为后续每轮调参的标准产物（看 Waiting/吞吐/KV/命中率的时序与对比）\n
- 若下一步要做容量评估，建议把“推荐并发点”的 P95 TTFT/E2EL 固化成门禁指标\n

## 六、下一步建议（更新后的压测矩阵）

1. **修复失败请求策略后，重跑基线**：batch_30 / 40 / 50（每组 1–2 次）\n
2. **压测矩阵建议**（围绕拐点做精细扫描，而不是再加更大并发）：\n
   - 并发：45、50、55、60（定位过载拐点更精确）\n
   - 参数：`max_num_batched_tokens` = 256 vs 512（至少在 50/60 各跑一组）\n
3. **如目标是“更高吞吐但不牺牲 TTFT 太多”**：优先考虑提升 Prefill 资源/实例数，再复测 60+ 并发是否仍进入 Waiting 上升区\n
